# ARCHITECTURE.md — India's Map

A static, frontend-first explorer for India's administrative geography, district-first.

Rationale for every choice below lives in [DECISIONS.md](DECISIONS.md).
Verified data facts live in [DATA.md](DATA.md).

---

## 1. Shape of the system

```
   OFFLINE (manual, versioned)                    RUNTIME (browser only)
   ────────────────────────────                   ──────────────────────

   OGD LGD API ──┐
   (needs key)   │
                 ├──►  pipeline/  ──►  public/data/lgd-2024/  ──►  src/
   india-geodata ┘         │                  │                     │
   release               reports/         static JSON            React app
   (pinned + sha256)   coverage.md      (~1.2 MB total)         MapLibre + Recharts
```

**One hard rule: the arrow only goes one way.** `pipeline/` writes `public/data/`.
`src/` reads it. They never call each other, and the frontend never talks to LGD, IGOD,
OGD, GitHub or bharatlas at runtime — not on load, not on interaction, not ever. Every
byte the browser sees was produced offline, reviewed and committed.

This is also what keeps the project's single secret contained: `DATA_GOV_IN_API_KEY` is
read by `pipeline/` only and cannot reach a browser bundle, because the bundle has no code
path that references it.

`pipeline/` has its own `package.json`. mapshaper and the OGD fetch code are build-time
tools; they must never appear in the frontend dependency graph.

Stages are plain `.ts` files run by **Node 24's native type stripping** (`node 03-normalize.ts`).
No transpiler, no bundler, no ts-node. Avoid TS-only runtime constructs (enums, namespaces,
parameter properties) — they are not erasable and will not run.

## 3. Pipeline stages

Run in order. Each stage is independently re-runnable and writes to disk, so a failure in
stage 04 does not force re-downloading 93 MB.

```bash
npm run all                 # 01→05, requires the API key
npm run all:geometry-only   # 02→05, works without it
```

| Stage | Input | Output | Key behaviour |
|---|---|---|---|
| `01-fetch-admin` | OGD API | `raw/ogd-lgd-districts.json` | Needs `DATA_GOV_IN_API_KEY`. **Dies with instructions if absent** — never falls back to hand-written data. Field names are unverified, so it probes documented candidates and fails with the real field list rather than mis-mapping. |
| `02-fetch-geometry` | `sources.json` | `raw/` | Downloads and **verifies SHA-256**. Mismatch = hard fail. Records the digest on first fetch. Idempotent: a matching cache is not re-downloaded. |
| `03-normalize` | `raw/*.geojson` | `build/` | Streams properties (93 MB never enters the JS heap), derives LGD ids, joins the attribute table back onto shapes via mapshaper, computes equal-area `areaKm2`. |
| `04-join` | roster + geometry | `build/hierarchy.json` | Joins **on `districtId` only**. Assigns `status`. Regenerates `reports/coverage-lgd-2024.md`. |
| `05-simplify` | `build/` | `public/data/lgd-2024/` | `-simplify 4% keep-shapes` → TopoJSON, writes the manifest, then runs **all validation**. |

### Validation invariants — the build fails if any is violated

Run by stage 05. Numbers in the logs (`[1]`…`[10]`) map to this list.

1. `districtId` values are **unique**
2. Every published feature carries a `districtId`
3. Feature count matches `expectations.publishedFeatureCount` minus documented exclusions — catches `-clean`-style silent drops
4. No fabricated geometry: every published shape traces to a source feature; roster districts without a polygon carry `no_boundary_published` and no invented shape
5. `stateId` agrees between geometry and `hierarchy.json`; exactly 36 distinct states/UTs
6. Extent reaches ≈37.08°N and ≈97.41°E (India-correct); union area within **±2%** of 3,287,263 km²; output within the size guard
7. TopoJSON round-trips through `topojson-client`, and the published object is named exactly `districts` / `states`
8. Every overlapping pair is documented in `geometry-fixes.json`; total overlap under the ceiling; every exclusion documented
9. The output directory contains **exactly** the four intended files — no strays, none missing
10. Manifest records source checksums and output digests

Invariants 3, 6 and 8 are what make a future data refresh safe: if upstream changes shape,
the pipeline stops rather than quietly shipping a wrong map. Invariant 8 was verified by
negative test — removing a documented overlap makes stage 05 exit 1.

**Never loosen an invariant to make a build pass.** Fix the data or the declarative
exception list.

### Two mapshaper traps, both load-bearing

- **`-dissolve` does not resolve overlaps.** It returns the sum of parts, so overlap reads
  as zero even when polygons genuinely stack. Union area must use **`-dissolve2`**
  (3,270,066 km², exposing 4,833 km² of overlap) not `-dissolve` (3,274,899 km², overlap
  invisible). This was caught during implementation and would otherwise have shipped a
  false "0 km² overlap" claim.
- **`-clean` silently deletes features.** On this dataset it drops Sanchor
  (`Retained 784 of 785`). It is never used.

## 4. Data contracts

Defined once in `pipeline/lib/schema.ts` with Zod, imported by both sides. The pipeline
validates on write; the frontend validates on read. A malformed file surfaces as a clear
error, not as a blank map.

```ts
const DistrictRecord = z.object({
  districtId:   z.string(),              // "549" | "unadministered:991"
  districtName: z.string(),              // "Udupi"        display only
  stateId:      z.string(),              // "29"
  stateName:    z.string(),              // "Karnataka"    display only
  sourceVintage: z.string().nullable(),  // year_stat, "" normalised to null

  sourceDistrictName: z.string(),        // raw dtname, preserved
  sourceStateName:    z.string(),        // raw stname ("KARNATAKA"), preserved
  censusDistrictCode: z.string().nullable(),  // dtcode11 — secondary key, never primary
  censusStateCode:    z.string().nullable(),
  areaKm2:      z.number().positive().nullable(),  // computed, never SHAPE_Area
  administered: z.boolean(),
  hasGeometry:  z.boolean(),
  status: z.enum(['active', 'no_boundary_published', 'dissolved', 'unreconciled']),
});
```

`status: "unreconciled"` exists because without the OGD roster we genuinely do not know
whether a district still exists. Guessing `"active"` would be an unverified claim, so the
pipeline refuses to make it.

The TopoJSON carries the identity and display fields; `hierarchy.json` carries the full
record including `areaKm2` and `status`. Join the two on `districtId`.

`manifest.json` carries vintage, per-source licence and checksum, derived counts, geometry
statistics, known gaps and known geometry issues. The UI reads it directly for the
provenance panel, so what is displayed is what was built.

## 5. Frontend

**Loading.** `hierarchy.json` (393 kB, attributes only) loads first so search and the table
are interactive immediately. `districts.topo.json` (981 kB) loads in parallel and decodes
via `topojson-client`. Both are static assets — cache-forever, and a new vintage is a new
directory, so cache invalidation is free.

**Map.** MapLibre GL JS with a GeoJSON source produced from the decoded TopoJSON. No
basemap, no tokens (D-009). District fills keyed on `districtId`; feature state drives
hover and selection. Zoom-to-district uses **bounding-box fitting, not centroids** —
Puducherry (Mahé, Yanam, Karaikal) and the Andamans are multipart, and a centroid can land
in the sea or in a neighbouring state.

**Routing.** `/`, `/state/:stateId`, `/district/:districtId`. URL is the source of truth for
selection, so every view is shareable and the back button behaves.

**State.** URL params plus local component state. No Redux, no global store — there is one
dataset and one selection.

**Accessibility.** Not an afterthought; the table view is a genuine equal-footing surface,
not a fallback. Districts are keyboard-reachable and screen-reader labelled. Colour is
never the sole carrier of meaning — `no_boundary_published` and `dissolved` get hatching
and explicit labels, not just a different fill. Palettes are colourblind-safe and checked
for contrast.

## 6. What V1 deliberately does not do

Subdistrict geometry (lazy-loaded per state; PMTiles becomes the right call at that scale),
block geometry (tabular only), the 1961→2025 historical series (no confirmed open source
yet), population overlays (Census 2011 is the last real enumeration; projections need an
explicit method and source or they should be omitted), and any authentication, database or
server-side component.

---

## 7. Refreshing the data

1. Update `sources.json` with the new upstream release URL and its SHA-256
2. Re-run stages 01→05
3. Read `reports/coverage-lgd-2024.md` — it diffs against the previous run
4. If invariants fail, **fix the pipeline or the fix list; never loosen the invariant**
5. New vintage → new `public/data/<vintage>/` directory; update the manifest pointer

Old vintages stay on disk. Boundary data is historical evidence, and being able to show
what a district looked like at a given snapshot is a feature, not clutter.

## 8. External dataset layer (spreadsheet-driven)

The per-district *dataset* panels (Speech / Text / Video / …) are a **separate data layer** from
the geographic pipeline above. They come from an external, sheet-shaped source through a provider
abstraction and are normalized into one long-form contract. Full detail: [DATASETS.md](DATASETS.md).

```
Google Sheets ─┐                                        ┌─ district aggregates → DistrictPanel
Excel (.xlsx) ─┤                                        │  (totals + subcategories, unit-aware)
demo CSV ──────┤→ DatasetProvider → DatasetRecord[] → aggregation engine
(PostgreSQL) ──┘   (source-specific)  (normalized)       │  (pure, memoized)
                                                         └─ state aggregates → StatePanel
                                                            (sum of districts, join by hierarchy)
```

- **Source-agnostic UI.** The DistrictPanel and DatasetPanels never branch on source type. Which
  provider runs is chosen in `src/data/datasetSource.ts` by configuration (Vite env) or a user
  action (uploading a workbook) — never in the UI.
- **Providers** (`src/data/datasetProvider.ts`, `excelProvider.ts`): `LocalDatasetProvider` (demo
  CSV, the safe fallback), `GoogleSheetsDatasetProvider` (published CSV URL), `ExcelDatasetProvider`
  (public .xlsx URL or an uploaded file, with worksheet selection). All funnel through one shared
  `normalizeRows` + Zod validation, so normalization is defined once.
- **Relationship to non-negotiable #5.** The geographic data still never leaves `public/data/`, and
  the app fetches nothing external *by default* — the demo CSV is same-origin. External fetching is
  strictly **opt-in**: it happens only when an operator sets a `VITE_*` URL (or uploads a file). No
  credentials ever live in the frontend; a private Google Sheet requires a future server-side
  provider and is refused client-side, not worked around.
- **Aggregation.** The sheet holds only atomic district rows; district and state totals are
  **derived** by a pure engine (`aggregateDatasetRecords.ts`), unit-aware (never sums across units),
  duplicate-excluding, with state totals summed from district totals via the hierarchy join
  (`districtId → stateId`). Memoized — recomputed only when the bundle changes.
- **Read-only.** External records are never written to `localStorage`; only the user's editable
  tree is. A manual *Refresh* replaces the in-memory bundle (rebuilding both aggregate maps)
  without touching selection, the user tree, or the MapLibre instance.
- **Future DB.** A `PostgresDatasetProvider` / API provider is the same interface again — the UI is
  unchanged. Deferred to a later phase.
